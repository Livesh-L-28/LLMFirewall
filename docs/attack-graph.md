# Attack Graph & AI Threat Modeling (Phase 33)

The **Attack Graph** layer builds directly upon the Phase 32 AI Security Knowledge Graph, advancing LLMFirewall from asking *"What architectural components exist?"* to analyzing *"How could these components be abused together in multi-step attack chains?"*

---

## 1. Architectural Philosophy

### Conservative Non-Exploitation Guarantee
A foundational security principle of LLMFirewall is:
> **Never assert that an attacker can definitely compromise a system based solely on graph relationships.**

Graph relationships demonstrate topological connectivity and theoretical exposure, not guaranteed compromise. LLMFirewall strictly categorizes attack paths into verifiable lifecycle states:

```text
POSSIBLE  ──>  OBSERVED  ──>  TESTED  ──>  CONFIRMED
(Candidate)   (Telemetry)     (Automated)    (Passed Tests)
```

### Layered Architecture
LLMFirewall does **NOT** introduce a second graph database or external service. The Attack Graph is a purely analytical layer operating over the local, zero-dependency `KnowledgeGraph`:

```text
                  Knowledge Graph
                         │
                         ↓
                 Attack Graph Layer
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
   Preconditions    Attack Steps      Techniques
        │                │                │
        └────────────────┼────────────────┘
                         ↓
                    Attack Paths
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
    Candidate          Tested          Observed
        │                │                │
        └────────────────┼────────────────┘
                         ↓
                    Mitigations
                         │
                         ↓
                  Security Gaps
                         │
                         ↓
                     Governance
```

## 2. Attack Path Statuses

Every path generated by the engine has an explicit, auditable status:

| Status | Definition | Criteria |
| :--- | :--- | :--- |
| `CANDIDATE` | Plausible sequence based on topology | Connects source to target, but missing proof of missing controls. |
| `SUPPORTED` | Preconditions verified in graph | Topology and absence of effective defensive controls verified. |
| `TESTED` | Corroborated by automated testing | Phase 30 red-team or security test suite verified multi-step chain. |
| `OBSERVED` | Confirmed by runtime telemetry | Verbatim sequence of security events witnessed in production. |
| `BLOCKED` | Neutralized by active security controls | Verified passing guardrails protect the chain against traversal. |
| `INVALIDATED` | Refuted by architectural drift | Architectural change broke connectivity or prerequisite. |

## 3. Evidence & Assumptions Tracking

### Verifiable Evidence Sources
No attack path or step is produced without explicit evidence attribution:

```python
class EvidenceType(str, Enum):
    GRAPH = "GRAPH"                      # Structural relationship in knowledge graph
    TEST = "TEST"                        # Security evaluation or red-team test outcome
    RUNTIME = "RUNTIME"                  # Runtime telemetry or observability security event
    CONFIGURATION = "CONFIGURATION"      # Snapshot or configuration verification
    POLICY = "POLICY"                    # Policy rule or missing guardrail specification
    FINDING = "FINDING"                  # Correlating vulnerability finding
    USER_PROVIDED = "USER_PROVIDED"      # Explicit threat modeling assumption or manual input
```

### Explicit Architectural Assumptions
LLMFirewall never silently converts assumptions into facts. Assumptions (e.g. *"Tool accepts agent-generated arguments without independent server-side validation"*) are tracked directly on attack steps and highlighted in threat models.

## 4. Threat Model of LLMFirewall Itself

When deploying an Attack Graph engine, the engine itself becomes a high-value target for adversaries. LLMFirewall documents and mitigates threats against its own attack graph engine:

### 1. Attack-Rule Poisoning
- **Threat**: An adversary injects malicious rules or modifies rule definitions to suppress true attack paths or cause denial of service.
- **Mitigation**: `AttackRuleRegistry` strictly validates rule structures, enforces unique IDs, validates techniques against `default_technique_registry`, rejects unknown entity types, and prevents cyclic self-loop rules.

### 2. False Relationship Injection
- **Threat**: Attackers attempt to register false nodes/relationships (e.g., claiming an unverified control protects an asset) to mask security gaps.
- **Mitigation**: Precondition evaluation requires cryptographically verified test passes (`passed=True`) before considering authorization controls effective. Untested controls remain `CONFIGURED`, never `PASSED`.

### 3. Graph Poisoning & Secret Infiltration
- **Threat**: Sensitive credentials (API keys, tokens) are stored in node properties to exfiltrate secrets via threat model exports.
- **Mitigation**: KnowledgeGraph strictly enforces secret pattern rejection on node creation and relationship assignment.

### 4. Path Explosion (Algorithmic Complexity Attack)
- **Threat**: Highly interconnected cyclical graphs cause exponential path explosion during traversal, exhausting CPU and memory.
- **Mitigation**: Bounded BFS traversal enforces strict limits: `max_depth` (default 5, max 20), `max_paths` (default 100, max 1000), `max_nodes_visited` (default 5000), and traversal timeout (default 10.0s). Visited node sets prevent revisiting nodes in the same chain.

### 5. Evidence Spoofing
- **Threat**: Fabricated test reports or spoofed telemetry events cause false `TESTED` or `OBSERVED` classifications.
- **Mitigation**: Multi-step test ingestion requires matching verified test results for *every single hop* in the chain before upgrading status. Partial test results leave downstream hops unverified.

### 6. Threat-Model Tampering
- **Threat**: Stored snapshots or threat models are altered post-generation.
- **Mitigation**: `AttackGraphSnapshot` computes a canonical SHA-256 digest over sorted path IDs, entry points, and trust boundaries, enabling drift detection and tamper evidence.

---

## 5. Non-Goals

LLMFirewall's Attack Graph is strictly a **defensive security analysis and modeling platform**. It intentionally does NOT implement:
- Autonomous offensive exploitation agents
- Real-world unauthorized attack payload delivery
- Automatic unverified blocking of production traffic without policy configuration
- Unbounded adversarial attack simulation
