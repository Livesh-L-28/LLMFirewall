# LLMFirewall Core v1.1.0 Architecture & Extension Review (Phase 43)

## 1. Executive Summary

This document presents the comprehensive architectural and extension review of **LLMFirewall Core v1.0.0** and establishes the technical blueprint and roadmap for **v1.1.0**.

LLMFirewall v1.0.0 successfully provides a lightweight, provider-agnostic, defense-in-depth security layer for Large Language Models, RAG pipelines, and autonomous AI agents. The codebase contains **172 Python source modules** across **26 subpackages**, **56 test modules** (with **611 passing tests**), 60+ documentation guides, and 21 runnable examples. It enforces zero mandatory external dependencies beyond Pydantic v2 and PyYAML, delivers sub-millisecond runtime protection (`~0.02ms` P50 overhead), and maintains zero credentials and zero unsafe `eval`/`exec` subprocess calls.

The Phase 43 audit reviewed the codebase across 20 distinct dimensions: public API integrity, coupling, extension points, detector design, decision pipelines, configuration, async/sync readiness, type safety, error models, performance, security design, framework integrations, CLI usability, documentation accuracy, test coverage, and backward compatibility.

## 3. Public API Analysis

The top-level `llmfirewall` namespace exports **468 unique public symbols** in `__all__`.

### Audit Findings & Resolutions:
1. **Unresolved Export `HASH_CHUNK_SIZE`**: `HASH_CHUNK_SIZE` was listed in `__all__` but omitted from the `supply_chain` import list in `__init__.py`. *Fixed in Phase 43.*
2. **Duplicate Export Names in `__all__`**: Six symbols appeared multiple times due to multiple feature phases: `IntegrationsConfig`, `PolicyDecision`, `SecurityEvent`, `SecurityEventType`, `protect`, `RuntimeDecision`.
3. **Symbol Shadowing in `__init__.py`**:
   - `PolicyDecision`: `llmfirewall.core.models.PolicyDecision` (Pydantic model) was shadowed by `llmfirewall.protection.models.PolicyDecision` (Enum).
   - `RuntimeDecision`: `llmfirewall.runtime.models.RuntimeDecision` was shadowed by `llmfirewall.protection.models.RuntimeDecision`.
   - `SecurityEvent` / `SecurityEventType`: `llmfirewall.observability.models` was shadowed by `llmfirewall.incidents.models`.
   - `protect`: `llmfirewall.integrations.base.protect` was shadowed by `llmfirewall.protection.sdk.protect`.

## 4. Architectural Coupling & Dependency Analysis

- **Imports & Circular Dependencies**: Zero circular imports exist in the release baseline. Modules cleanly import downwards from `core` and `detectors` into engines.
- **God Class / God Facade**: `Firewall` in `src/llmfirewall/firewall.py` contains 1,386 lines with 25+ lazy properties (`rag_quarantine`, `model_verifier`, `dependency_scanner`, `integrity_manager`, `governance_engine`, etc.).
  - *Recommendation for v1.1*: Retain `Firewall` as the stable developer facade for backward compatibility, but group subsystem property instantiation into modular service providers.
- **Hidden State & Singletons**: `default_detector_registry` and `default_tool_registry` provide module-level defaults. They are safe for single-tenant use, but multi-tenant deployments need explicit instantiation. `Firewall(config=...)` properly isolates internal instances.

## 5. Extension Point Analysis

Developers currently extend LLMFirewall through:
1. **Detectors**: Subclass `Detector` (which now subclasses `BaseDetector`) and register via `DetectorRegistry.register()` or pass directly to `DetectorEngine([custom_detector])`.
2. **Tool Permissions**: Register tools with `ToolRegistry` and configure JSON schemas, regex constraints, and command/SQL rules.
3. **Policies**: Declarative YAML/JSON policies defining custom rules, threat types, and condition logic.
4. **Approval Providers**: Implement `ApprovalProvider` Protocol for human-in-the-loop or external approval mechanisms.
5. **Event Storage**: Subclass `EventStore` (in-memory, JSONL, SQLite available).
6. **Telemetry**: Implement `TelemetrySink` ABC.
7. **Discovery Providers**: Subclass `DiscoveryProvider` for inventory discovery.

*v1.1 Target*: Add explicit `typing.Protocol` interfaces for custom detectors, policy evaluators, and external intelligence providers to allow duck-typing without forced inheritance.

## 6. Detector Architecture Review

The detector execution follows:
```
Text / Request
     ↓
DetectorEngine.execute()
     ↓
Detector.detect(text, context)
     ↓
List[Finding] (frozen Pydantic models)
     ↓
FindingCollection
     ↓
RiskEngine.evaluate() -> RiskScore
     ↓
PolicyEngine.decide() -> PolicyDecision
```

### Strengths:
- Invariant "Detectors only detect" is strictly respected: detectors never make allow/block decisions or raise policy exceptions.
- `Finding` objects are immutable (`ConfigDict(frozen=True)`).
- `DetectorEngine` supports `fail_fast=False` with isolated per-detector error capture into `errors` list.

### Opportunities for v1.1 (Phase 44 & 45):
- Add pre-filter token/regex indexing before full detector passes.
- Support confidence calibration across multi-pattern findings.

## 7. Security Decision Pipeline

The decision precedence is strictly defined and verified:
`BLOCK` > `REDACT` > `WARN` > `ALLOW`.

- Redaction is performed via `SafeRedactor` with exact span offsets and replacement templates.
- Processed text invariant: When blocked, `processed_text` is empty `""`. When redacted, `processed_text` contains redacted placeholders. When allowed, it contains clean text.
- Telemetry invariant: `safe_dict()` automatically redacts `original_text` and matched secret substrings before exporting or writing to audit logs.

---

## 8. Configuration Audit

- Configuration models (`FirewallConfig`, `DetectorConfig`, `RiskConfig`, `PolicyConfig`, `RuntimeConfig`, `RAGConfig`, `SupplyChainConfig`, `AgentCapabilitiesConfig`) are strictly validated via Pydantic v2 with `extra="forbid"`.
- Monotonic risk threshold ordering is strictly enforced by `@model_validator` on `FirewallConfig`.
- Serialization: Safe `yaml.safe_load` is enforced across all YAML ingestion paths.
- Default behavior: Secure by default (`fail_fast=False` for detection robustness, `FailBehavior.FAIL_CLOSED` for runtime protection, `PolicyMode.ENFORCE`).

---

## 9. Sync vs. Async Audit

- **Synchronous Path**: Core regex detection, text normalization, risk aggregation, and policy rules execute synchronously in CPU-bound microsecond intervals (`<1ms` for standard prompts).
- **Asynchronous Path**: Present in:
  - ASGI middleware (`FirewallMiddleware`) for FastAPI / Starlette
  - `RuntimeEngine.async_session` and `RuntimeSession.guard_stream_async`
  - `GovernanceEngine.evaluate_async`
  - Integration wrappers `@protect` supporting coroutines
- **v1.1 Recommendation**: Do NOT convert CPU-bound regexes into async coroutines (which adds event-loop scheduling overhead). Instead, add native async streaming scanner `Firewall.scan_stream_async()` for streaming LLM tokens in Phase 48 and 52.

## 10. Type-Safety Audit

- Public signatures throughout `src/llmfirewall` utilize comprehensive type annotations (`typing.Optional`, `List`, `Dict`, `Union`, `Callable`, `Any`).
- Pydantic v2 models provide strict runtime type coercion and validation.
- Standard for v1.1: Replace generic `Dict[str, Any]` in public callback signatures with typed `TypedDict` or Protocols where practical.

## 11. Error Model Audit

### Exception Hierarchy:
```
Exception
   └── LLMFirewallError
         ├── ConfigurationError
         │     └── PolicyValidationError
         ├── BlockedPromptError
         ├── BlockedOutputError
         ├── SecurityBlockError
         ├── IncidentError
         ├── RuntimeSecurityError
         │     └── RuntimeLimitExceeded
         └── SecurityGateFailure (Subclassed in Phase 43)
```

- Every framework exception now inherits from `LLMFirewallError`.
- Clear separation maintained between:
  1. Policy denials (`BlockedPromptError`, `BlockedOutputError`, `SecurityBlockError`)
  2. Input validation/configuration failures (`ConfigurationError`, `PolicyValidationError`)
  3. Runtime loop/resource limits (`RuntimeLimitExceeded`)
  4. Governance gate failures (`SecurityGateFailure`)

## 12. Security Architecture Review

| Risk Category | Severity | Current Status | Assessment & Mitigation |
| :--- | :--- | :--- | :--- |
| Untrusted Code Execution | CRITICAL | **Mitigated (PASS)** | Zero dynamic `eval()` or `exec()` in framework codebase. Models inspected for pickle/PyTorch safety before loading. |
| ReDoS (Regex Denial of Service) | HIGH | **Mitigated (PASS)** | Max scan text length bounded at `MAX_SCAN_TEXT_LENGTH = 5MB`. Regex patterns use anchored, non-backtracking structures. |
| Fail-Open Risk | HIGH | **Mitigated (PASS)** | Production runtime policies default to `FAIL_CLOSED`. |
| Credential & PII Leakage | HIGH | **Mitigated (PASS)** | Audit logs and `safe_dict()` omit raw text and matched secret tokens. Synthetic keys used in all test suites. |
| Deserialization Vulnerability | HIGH | **Mitigated (PASS)** | `yaml.safe_load` strictly enforced everywhere; PyYAML `Loader` unsafe modes forbidden. |
| CLI Terminal Injection | MEDIUM | **Mitigated (PASS)** | ANSI control codes and non-printable bytes stripped by `sanitize_terminal_text`. |

## 13. Integration Architecture

- Integrations with FastAPI, Flask, Django, LangChain, and LlamaIndex use clean optional dependencies defined in `pyproject.toml`.
- Third-party packages are imported lazily inside `IntegrationRegistry` or adapter functions; core `llmfirewall` imports succeed with zero optional dependencies installed.
- In-memory mock providers and fallbacks allow test suites and offline CI to run without live cloud connections or GPUs.
