## 1. Overview & Release Objective

LLMFirewall Core v1.1.0 delivers an enterprise-grade expansion of the LLMFirewall open-source security framework. The release addresses emerging threat vectors identified in real-world LLM deployments, including sophisticated obfuscated prompt injections, multi-turn conversational probing, compound attack chains across tools and data stores, and high-throughput streaming serving requirements.

## 2. Major Architectural & Subsystem Enhancements

### 2.1 Detection Engine 2.0 (`llmfirewall.detectors`)
- Multi-stage detection pipeline: Normalization → Heuristic Pre-Filtering → Execution Planning → Parallel/Sequential Inspection → Finding Aggregation.
- Structural typing protocol `DetectorProtocol` enabling custom third-party detectors without framework inheritance.
- SHA-256 fingerprint finding deduplication and span conflict resolution.

### 2.2 Advanced Prompt-Injection Defense (`llmfirewall.detectors.prompt_injection`)
- Unicode homoglyph translation table (Cyrillic, Greek, mathematical alphanumeric symbols to canonical ASCII).
- Stripping of invisible zero-width spaces (`\u200b`), zero-width joiners (`\u200d`), and BiDi directional override markers (`\u202e`).
- Leetspeak substitution normalization.
- Structural role confusion and instruction override boundary detection.

### 2.3 Performance & Caching Engine (`llmfirewall.cache`)
- Deterministic, bounded LRU `ScanCache` with TTL expiration.
- Ephemeral context filtering: Session IDs, nonces, and timestamps do not fragment cache entries.
- Compiled `RegexCache` avoiding repeated pattern recompilations.
- Empirical benchmark: **8.1x speedup** on warm cache hits (`0.038 ms` median latency).

### 2.4 Risk Intelligence 2.0 (`llmfirewall.risk`)
- Multi-turn `SessionRiskTracker` with exponential temporal decay ($\lambda = \ln(2) / T_{1/2}$) detecting slow-and-slow probing.
- `FindingCorrelationEngine` inferring compound multi-stage attack chains.
- `BlastRadiusEstimator` calculating systemic exposure and prescribing immediate containment actions.

### 2.5 Developer Integrations 2.0 (`llmfirewall.integrations`)
- Zero-dependency pure ASGI 3.0 middleware `LLMFirewallASGIMiddleware` supporting streaming body inspection and WebSockets.
- Sliding-window `StreamingTextGuard` inspecting real-time LLM token streams.
- Unified synchronous and asynchronous client SDKs (`LLMFirewallClient`, `AsyncLLMFirewallClient`).

### 2.6 Policy-as-Code 2.0 & Static Linter (`llmfirewall.policy`)
- `PolicyLinter` analyzing policy documents for shadowed rules, logical contradictions, cycles, and invalid regex patterns.
- Multi-condition rule predicates (`min_confidence`, `category`, `direction`, `min_findings_count`).

### 2.7 Observability & SIEM Integration (`llmfirewall.observability`)
- Programmatic `SecurityDashboardAPI` for posture aggregation, time series bucketing, and paginated event queries.
- Common Event Format (CEF) SIEM exporter (`export_events_cef`) for enterprise SIEM ingestion (Splunk, ArcSight, QRadar, Sentinel).
- Prometheus cache hit/miss telemetry.

### 2.8 Adversarial Evaluation Engine (`llmfirewall.eval`)
- `AdversarialMutationEngine` generating randomized adversarial attack variants.
- `AdversarialRedTeamRunner` clustering bypass failures into `FailureCluster` reports.

## 5. Backward Compatibility & Public API Invariants

1. **Zero Breaking Changes**: All v1.0.0 imports, classes, functions, and config options remain fully supported.
2. **Deterministic Evaluation**: Policy resolution precedence remains `BLOCK > REDACT > WARN > ALLOW`.
3. **Fail-Closed Default**: `FailBehavior.FAIL_CLOSED` guarantees that traffic is blocked under unexpected internal exceptions.
4. **PyPI Distribution / Import Identity**: Distributed on PyPI as `llmfirewall-core`, imported as `import llmfirewall`.

---

## 6. Known Limitations

1. **Deterministic Heuristic Boundaries**: Detection engines operate on deterministic patterns and entropy calculations. They do not claim universal defense against all novel, zero-day adversarial attacks.
2. **Context Window Slicing in Streaming**: Sliding window inspection may miss adversarial triggers that span across buffer overlap boundaries exceeding the configured window overlap size.
3. **In-Memory Cache Scaling**: `ScanCache` is an in-memory process-local cache. In multi-process worker architectures, each worker maintains its own local cache unless backed by an external distributed cache.
